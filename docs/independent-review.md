# 独立 Review 门禁

## 为什么需要独立检查

Design 与实现的作者都容易沿着自己的既有假设检查。Design 作者可能看不出文档仍依赖对话上下文、存在互相矛盾的章节或允许两种实现解释；实现 agent 则可能漏掉“局部存在但没有接进生产路径”的问题，也可能把当前示例、固定 ID、顺序或数据集误当成领域规则。独立 reviewer 应从成品和真实仓库重新建立判断，而不是相信作者的完成摘要。

真实项目中，独立检查曾发现 selector 和 pass 已存在，但 render object 没有进入 shadow caster 集合；也发现失败前置校验发生在文件复制之后，留下孤儿文件。这些问题仅检查符号或 happy-path 测试很难发现。

## Design Review

Design 达到候选 Ready 后，由只读 subagent 审查最终 `design.md`。输入只包含 Design 路径、项目根目录和 Design Review 合约，不传入主 agent 的完成结论、怀疑点或讨论 transcript。这既检查内容完整性，也检查文档是否真正自包含。

Reviewer 对照真实生产边界检查架构、接口、数据结构、所有权与流向、失败和生命周期行为、验证、命名语义、歧义、过度设计与样例过拟合。命名检查分为两层：明确的项目命名规则必须引用规则并严格执行；领域概念、稳定接口和所有权/生命周期边界只有在能够证明“名称暗示 → 实际职责 → 实质误解或误用”时才形成语义 finding。不得把示例扩展成关键词黑名单，也不审查示意代码中的偶然局部措辞。Reviewer 不改文档、不替用户选择方案。P0/P1 或缺少必要证据会阻断最终用户门禁；处理方式不唯一时回到 Design 讨论。P0/P1 修订必须重新派审，P2 的局部非实质修正不需要重复审查。

## Implementation Review 的同一工作区

Reviewer 必须读取实现所在的共享工作区。为 Review 创建隔离 worktree 会让 reviewer 看不到未提交的真实改动，产生虚假的安全感。Reviewer 只读，不替主 agent 修代码。

## Review 顺序

1. 从 Design 的每个成功标准建立覆盖表。
2. 把 Design 指定的验证入口、实际 diff 和可复现的原始输出交叉核对，不把主 agent 的完成标记当作事实。
3. 从外部入口沿真实运行时/编辑器路径追踪到变更点。
4. 从 Design、公开契约和领域模型确定预期输入类别，改变与语义无关的名称、ID、顺序、数量、尺寸和样例值，检查实现是否仍由同一不变量驱动；协议、格式或领域明确规定的常量不算过拟合。
5. 检查失败、清理、所有权、兼容和版本控制边界。
6. 对新增或改名的项目自有符号先执行适用的项目明确规则，再只对领域类型、稳定接口、所有权/生命周期边界和核心逻辑符号做语义检查。命名 finding 必须给出“名称暗示、实际职责、具体后果”证据；名词动词组合、某个前缀或 reviewer 的个人表达偏好本身都不是 finding。BCL、第三方及框架强制签名不在此限制内。
7. 验证证据确实证明一般规则，而非只证明文件存在、构建通过或已知样例通过。

P0/P1 或未满足成功标准必须阻断完成。若修复方式不唯一，主 agent 回到用户决策，而不是 reviewer 或主 agent自行挑选方案。
