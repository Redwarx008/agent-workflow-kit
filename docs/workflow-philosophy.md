# AI 协作工作流哲学

## 文档是基础设施

对 agent 而言，稳定的设计、决策和经验文档不是事后说明，而是跨会话恢复上下文、保持术语一致和避免重复犯错的基础设施。代码说明系统现在做什么；Design 和决策记录说明为什么这样做、哪些边界不能被随意改变。

## 架构先于实现

实现速度会放大设计质量。真正会改变行为、契约、数据语义、兼容或验证强度的边界没有讲清楚时，快速编码只会更快地产生耦合与返工。Design 阶段不为未受影响的领域填模板；但改动只要触及架构、生产接入、接口、数据结构、所有权或数据流，就必须向用户展示并讨论对应目标，即使仓库证据只支持一个方案。最终文档仍保持最小充分：只保留已选定且会约束实现或验收的结果。

Design 的边界由用户选择的一次交付和授权范围决定，不按目录、模块、调用路径或技术可拆性机械拆分。同一个结果依赖的 Runtime、Editor、Bake 或其他生产路径应保持一致语义；用户也可以把技术上独立的目标放进同一份 Design。此时分别说明成功标准和证据，并诚实区分共享不变量、必要协调与单纯同批交付。只有组合范围会掩盖不同结果、授权/发布边界、破坏性后果或可审阅完成度时，agent 才建议拆分，最终仍由用户决定。

参考实现的差异只是调查线索，不是项目缺陷的证明。开放式评估先查清当前生产可达性和真实后果，再由用户选择哪些发现进入实施范围；明确的实施目标则不重复询问。Design 可以在证据和用户确认下以无需实施归档，避免工作流为了进入 Act 而制造改动。

## 失败记录比成功叙述更有价值

成功方案可以从代码重建；失败尝试如果没有记录，后续 agent 会在相同假设上重复消耗。记录失败时应包含症状、证据、因果机制、为什么失败，以及什么条件变化后才值得重试。

## 会话延续必须系统化

不要依赖单个对话无限增长。项目应有稳定的启动阅读顺序、活跃 Design、会话结束记录和可复用 learnings。不要把 agent 的机械执行过程固化为另一份工作流账本；原始工具状态只在当次工作需要时存在，长期价值应压缩成项目决策或经验。

## Slop 公式

`Slop = agent 速度 × 约束缺失 × 无验证 × 文档不足`

提高模型速度无法解决 slop；真正的杠杆是明确边界、选择能证明行为的验证、持续维护项目记忆，并用独立 Review 检查声明与生产路径之间的落差。
